## 1. 三类已修缺陷：现场 → 根因 → 修复 → 判据

### 1.1 A：类切换未过滤 RT 任务 ⇒ brk #0x800

- 现场：t162（opt150）/ t176（opt154）/ t177（opt155）三次硬挂，PC 分别落在 `ext_ctrl+0xc68`、`ext_ctrl+0xcc0`、`__schedule+0x7e8`；崩溃形态是 `brk #0x800`（SCHED_WARN_ON）。
- 根因（因果链）：
  1. 我们把参照补丁里的 `if (reject_change_to_scx(p, p->prio)) continue;` 过滤删掉了（参照补丁重建产物 refwork/ref/kernel__sched__ext.c:3141-3143），于是 RT 任务被切进 hmbird 类；
  2. `hmbird_check_class_changed` → `switched_from_rt`（kernel/sched/rt.c:2632）→ `rt_queue_pull_task`（rt.c:2644）→ `queue_balance_callback`（rt.c:439 挂 rt_pull_head）；
  3. kernel/sched/core.c:2304-2305 的契约要求 `check_class_changed()` 之后必须 drain 回调；我们只在切类循环**外** drain（hmbird.c:5058）；
  4. 循环内其它 CPU 的 `rq_pin_lock`（kernel/sched/sched.h:1679）因此炸断言。
- 修复（opt158）：在 enable 与 disable **两个**切类循环里各加 `if (reject_change_to_hmbird(p, p->prio)) continue;`。参照补丁的策略是「不产生回调」——它全树零 drain 代码（grep `__balance_callbacks` 只命中 core.c:240）。
- 判据（t183，opt158，hmbird ON + 4 线程 + 60s）：balance_cb=0 / ext_ctrl=0 / task_rq_lock=0 / __schedule=0 / stall=0，boot_id 未变（`fbde553d-e91e-4db3-84a2-92bc82b1495d`）。对照 opt154/opt155 五项各有命中。
- 对抗审核（wb-5）留下的两条限制：
  - opt155 的 drain 落在 `hmbird_tasks_lock` 临界区内（违反「锁内只记录、解锁后执行」）；
  - 单次 drain 不是不动点（core.c:5201-5229 在调 func 前就把 `rq->balance_callback` 置 NULL，drain 期间可被重挂 ⇒ 有残留）。这解释了 opt155 只部分有效。
- ★不要照抄参照补丁去掉 drain★：参照补丁的 ext.c:1319-1336 与我们逐行相同，但它靠上游「同一个 rq 不立即重锁」成立；我们每轮重锁同一 rq。
- 出处：成功-opt158修复balance_callback断言.md:7-29（t183 判据）、:33-51（根因与修法）、:72-82（三次同源）。

### 1.2 B：T2 簇可见性缺口 ⇒ 任务饿死 ⇒ 内核自禁

- 现场：t169/t172（opt152，8 线程 600s）出现 `failed to run for`，android.bg 饿死 167.208s / 120s，随后内核自动禁用 hmbird。
- 根因（wb-8/t90 定量对账）：gdsq 入队总和 199,293 / 消费总和 137,086 / 缺口 62,207；逐桶 5:47、6:57、7:53258、8:8821、9:24，合计恰好 62,207。`gdsq[7]` 入队 53362 / 正常消费仅 104（99.8% 是迟到消费）；`gdsq[8]` 入队 55738 / 正常消费 46917（差 451 倍）。`gen_cluster_ctx_separate`（档案行号 :1197-1229）给 BIG 的窗口 [5,8)、LITTLE [8,10) ⇒ 各簇只能扫一半，等待无上界；android.bg（cgroup bg → gdsqs[9]，`cgrp_name_to_idx`:1683-1687）恰好落在只有 LITTLE 可见的那一半。
- 修复（opt159）：在 `consume_timeout_dsq` 内、只放宽超时兜底路径：`ctx.lower = NON_PERIOD_START(5)`、`ctx.upper = NON_PERIOD_END(10)`。
- 判据（t184，opt159，8 线程满载 200s，跨 120s 阈值）：stall=0 / balance=0 / disabled=0、scx=1 全程、runq=10~16，boot_id 未变（`57197068-73e6-41a7-b73e-493aa337632b`）。
- 出处：成功-opt159修复饿死缺陷.md:7-23（t184）、:27-34（历史对照）、:54-72（T2 定量）。

### 1.3 C：诊断数据假 → 真

- 现场：`hmbird_stats` 全 0，曾被当成「hmbird 什么都没做」的证据。
- 根因（wb-4/t87 + wb-6/t88）：该节点是硬编码假数据（`hmbird_sched_proc_main.c:324-370` 全是 `seq_puts(m, "...:0, 0")`），**不是 OPPO 原厂代码**，而是社区移植版带入的 stub（commit `2c90fce1fc78`，2026-10-08 opt57 step 5a，与社区文件逐字节相同）。
- 修复（opt156，并入 opt159 验证）：换成调用现成的 `stats_print()`（hmbird.c:432）+ 打开 `slim_stats` 门控。
- 判据：total_dsp_cnt=205868、timeout_cnt=53234（真数据）。
- 出处：成功-opt159修复饿死缺陷.md:74-95。

### 1.4 D（附）：每 60s 周期强切 governor

- 现场：hmbird 在线期间，watchdog work 每 60s 把 governor 从 scx 抢回 uag，守护（POLL_SEC=4）再设回 ⇒ `cpufreq_set_policy()`（drivers/cpufreq/cpufreq.c:2571）走完整 exit+init+start，scx 调速器反复销毁重建（注销/重注册 walt 回调）。实测一局 6m41s 重建 6~7 次、间隔均值 61.4s。
- 根因：原 t42 依据（「hmbird + scx 会硬挂，所以必须周期强切」）不成立 —— ① 同内核 opt138 的四格矩阵 60 样本判「卡死=否」；② 当时 `reject_change_to_hmbird` 只有定义、两个切类循环都没调用（即缺陷 A），2026-10-10 20:46 的现场与缺陷 A 无法区分；③ 20:46 现场有 4 个并发诊断脚本。
- 修复（opt160）：把 watchdog work 内的 `if (atomic_read(&__hmbird_ops_enabled)) hmbird_gov_switch_away();` 用 `#if 0` 包起来；保留启用前的一次检查作兜底（档案行号 hmbird.c:4924 的 `if (!hmbird_gov_switch_away()) { … hmbird_gov_restore(); return -EBUSY; }`）。
- 判据（二进制）：`llvm-objdump -d --disassemble-symbols=hmbird_watchdog_workfn vmlinux | grep -c cpufreq` ⇒ 0（周期路径已无 cpufreq 调用）。
- 出处：成功-opt160停用周期强切governor.md:11-13、:19-28。

## 3. 两条被证伪的假设

### 3.1 假设「hmbird 一开就坏」（已证伪）

- 反证：wb-hm 全表统计 hmbird + scx 共 9 次实验、成功 6 次（含矩阵 60 样本、t144 四轮 8 核满载、t145 存活 170s、opt159 真实游戏 6m41s），失败 3 次中 2 次已归因到别的缺陷（缺陷 A 契约违反、fair.c:5004 se==NULL）。
- 另有源码级记录支持「hmbird + scx 致命」的旧结论（hmbird.c:3513-3520，2026-10-10 20:46 进游戏硬挂整机），但该现场与缺陷 A 不可区分 ⇒ 不能作为「hmbird 本身有毒」的证据。
- 出处：成功-opt160停用周期强切governor.md:19-28。

### 3.2 假设「nr_running 泄漏」（已证伪）

- Q1 不泄漏：`add_nr_running(rq,1)`（档案行号 hmbird.c:2443）与 `sub_nr_running(rq,1)`（:2520）由同一个 `HMBIRD_TASK_QUEUED` 位门控；该位全树只有两个写点（:2441 set、:2517 clear），其余 8 处只读 ⇒ 不产生单向计数。
- ★行号漂移提醒★：当前 HEAD（opt162）同一逻辑行号为 set hmbird.c:2488 / clear :2564（test 点在 :2481/:2545/:2998+）。引用时务必写清树版本。
- Q2（t177 的 runq=901）记为「未复现、原因未定」：① t179/t181 同镜像不复现；② kernel/sched/loadavg.c:78-91 `nr_active = this_rq->nr_running - adjust` ⇒ load 与 runq 同源，不是独立证据；③ t177 以 kernel crash 收尾 ⇒ 读数来自已损坏镜像。
- 附带更正：t71 说「hmbird 从不调用 sub_nr_running」与源码不符（:2520 明确调用）⇒ 其方案 c 不应采纳。
- 出处：成功-opt158修复balance_callback断言.md:110-144。

## 4. 两次「只看现象就归因」的翻车

### 4.1 把硬编码假数据当诊断（opt156 之前）

- 现象：`/proc/hmbird_sched/hmbird_stats` 全是 0。
- 错误归因：据此判断 hmbird 没有在做任何调度工作。
- 真相：该节点是社区移植版带入的 stub，恒为 0（`hmbird_sched_proc_main.c:324-370`）⇒ 与 hmbird 实际行为无关。
- 教训：**先验证观测口本身**，再解释观测值。修复后才拿到 total_dsp_cnt=205868。

### 4.2 把厂商 TEE 的 Call trace 当 WARN（opt162 轮）

- 现象：诊断脚本 `warn=` 计到 2，看起来「有内核警告」。
- 真相：`dmesg | grep -n 'WARNING:'` 只有一条开机期的 `Unprivileged eBPF is enabled…`；那些 `Call trace:` 是**厂商 TEE 的周期栈打印**，每 ~61.4s 一次（121.84 / 183.28 / 244.72 / 306.16），栈为 `__switch_to+0x15c → __schedule+0x798 → schedule_timeout+0x30 → wait_for_common+0xd8 → wait_for_completion+0x18 → __scm_smc_call+0x23c [qcom_scm] → qcom_scm_invoke_smc+0xac → prepare_send_scm_msg+0x24c [smcinvoke_dlkm] → process_invoke_req+0x998 [smcinvoke_dlkm]` ⇒ 与调度无关、任何内核上都有。
- 教训：warn 判据要收窄成 `WARNING:`，不要用裸 `Call trace` 计数。
- 出处：成功-opt162上机验证.md:68-88。

## 6. 16:55 静默硬挂（★根因未定★）

### 6.1 现场

- 设备 RMX3888 / opt161b；前一次 boot_id `b2b75be3-4a29-4196-ae42-96178e06f519`（16:16 起），重启后 `53619f39-9404-4bfc-8e21-7e5cb5a6a2af`；`/proc/last_boot_reason = kernel crash Minidump [2026-10-13 16:55:58]`。
- 用户亲述：「我手动退出了游戏，想要点外卖，然后手机就卡死重启了」。
- 时间轴：~2331 用 monkey 拉起游戏（第五人格，GAMEPID=6804）→ 用户手动退出游戏去开外卖 App → **2365.066257** t194-enter.sh 启用 hmbird（`scx_enable=1 -> hmbird_ctrl() rc=0, enabled=1`）→ 2368.343971 内核日志最后一条（普通触摸屏日志）→ 16:55:58 重启 → 16:56:31 新 minidump 落盘（56 MB）。

### 6.2 已确证

- 与 16:13 那次**不是**同一路径（critical.log 无 16:5x 的 `<multimedia-SF Hang-begin>`）⇒ 不是 OPPO 的 SF Hang 看门狗判定。
- 崩溃形态是**裸 kernel_panic**（critical.log:142859-142863，无 cause / 无 COMM / 无 FST_FRAME），与 2026-10-13 01:11:55 同形。
- 转储解析（255,926 行）：Kernel panic=0 / Unable to handle=0 / BUG:=0 / hung task=0 / sysrq=0；Call trace=10（全部是开机阶段 proc_register 警告）⇒ 内核**从头到尾没打印任何 panic/oops/BUG/hung task** ⇒ 静默硬挂。
- hmbird 完整开关周期都在转储里：`enabled finished`（jiffies 4295483557，utime 2365.066）与 `disabled finished`（jiffies 4295484410，utime 2368.477）+ 配对的 `scx_enable=0 -> hmbird_ctrl() rc=0, enabled=0` ⇒ **回滚确实成功执行并成功返回**（先前「卡死在回滚的同步调用上」的推断已被推翻）。
- 本机 SF Hang/重启是复发型问题（2026-10-09 21:40、2026-10-13 01:35（那次已证 hmbird=0、gov=uag）、16:13）。
- 本次 governor 全程 uag ⇒ 即使 hmbird 有责，也是「hmbird 单独」而非「hmbird + scx」。

### 6.3 未确证 / 强混淆项

- ★「hmbird 导致本次卡死」未证实★；唯一剩下的是「时间上紧邻」：2368.477 disabled 之后 ≤0.1s 内核停止输出，≈30s 后重启。
