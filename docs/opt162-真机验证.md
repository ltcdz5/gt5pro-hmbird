- 90 s 内**零** `err_exit` / `hmbird_ops_error` / `failed to run for`；无 `t42:` 强切、无自禁；
- 自动回滚到 `partial_util=N` + `scx_enable=0` + `gov=uag`，`boot_id` 未变。

★结论★：`_changelog_append_20261011.md:30` 记的「opt142 置 0 后 8 s 内 running 2→22、61 s 后自检 stall 并自禁」**在本轮条件下未复现**。两种解释待分：

(a) 当时是**高负载**场景（有自旋线程），本轮 load 只有 4~6，partial 机制没被触发；
(b) 当时的自禁来自别的并发变量。

⇒ 要判死需要一次**带 8 线程负载**的 Y 臂（**未做**）。

## 五、噪声澄清：那几条 `Call trace:` 不是内核 WARN

窗口内 `dmesg | grep -n 'WARNING:'` 只有一条，且是开机期的：

```
[15.365405] WARNING: Unprivileged eBPF is enabled, data leaks possible via Spectre v2 BHB attacks!
```

而 t194 脚本 `warn=` 计到 2 的那些 `Call trace:` 实测是**厂商 TEE 的周期栈打印**，每 ~61.4 s 一次（121.84 / 183.28 / 244.72 / 306.16）：

```
Call trace:
 __switch_to+0x15c/0x2ec
 __schedule+0x798/0xbc4
 schedule_timeout+0x30/0xec
 wait_for_common+0xd8/0x1a4
 wait_for_completion+0x18/0x24
 __scm_smc_call+0x23c/0x510 [qcom_scm]
 qcom_scm_invoke_smc+0xac/0x130 [qcom_scm]
 prepare_send_scm_msg+0x24c/0x794 [smcinvoke_dlkm]
 process_invoke_req+0x998/0x1330 [smcinvoke_dlkm]
```

⇒ 与调度无关、任何内核上都会出现。★脚本的 `warn` 判据应只数 `WARNING:`，别把 `Call trace:` 算进去★。

- opt162 镜像与部署链路（CRC 四门禁 + 打包 + deploy v10）**端到端可用**；
