# 判据与陷阱

> 一页纸：**动手前**读一遍，**读结论前**再读一遍。这里每一条都是踩过的坑。
> 内核行号基于 HEAD `7cc87ec0d8dc`（分支 `opt162`）；换镜像后先重新 `grep`。

## 一、实验纪律

1. **单变量**：一次只改一个东西。四格矩阵要能对照；不要在同一窗口里并发跑多个诊断脚本（历史事故 2026-10-10 20:46 现场有 4 个并发诊断脚本，导致根因无法归因）。
2. **先读后写**：先只读盘点、记录基线（governor / `scx_enable` / `slim_stats` / `dmesg` 行数 / `t42` 计数 / `boot_id`），再动手改。
3. **产物先过独立复核再上机**：补丁、上机脚本、公开文档，先交**没有参与编写**的人独立核对，再拿去跑／发布。
4. **每轮同时有人回答「为什么」**：只做实现不做归因，会把「现象消失」误当成「根因修复」。
5. **每条结论给 `文件:行号` 或反汇编地址**：给不出就是还没结论。
6. **不确定就写「未验证」**：不许编造数字、md5、行号。「未复现」也不等于「不存在」。
7. ★**禁止「树里没有 ⇒ 设备上没有」**★：我们在这一点上犯过两次。厂商模块是**独立编译**的，内核树里 grep 不到某个符号，不代表设备上的 `.ko` 里没有；要下「设备上没有」的结论，必须用**设备侧**证据（全量 `nm` 扫描、`strings`、实测行为）。
8. ★**使用任何数据前，先确认它的产生方式**★（D9）：曾经把 `/proc/hmbird_sched/hmbird_stats` 的读数当诊断依据，后来发现那一段是**硬编码假数据**（`hmbird_sched_proc_main.c:324-370` 全是打印 0 的字面量），opt156 才改成调用真 `stats_print()`。**看着干净的数字，可能根本不是测出来的。**

## 二、假 PASS 陷阱（三条）

### 1. `slim_stats != 1` ⇒ 统计被门控 ⇒ 增量恒 0

统计记录函数在 `slim_stats` 为 0 时**直接返回**：

- `hmbird.c:345`：`if (!slim_stats)` ⇒ 记录侧提前返回；
- `hmbird.c:371-377`：`slim_stats_record()` 里 `if (!slim_stats) return;`；
- 出厂默认是 **0**（`hmbird_sched_proc_main.c:42` 的变量、`:415` 的节点）。

⇒ 忘了 `echo 1 > /proc/hmbird_sched/slim_stats`，你会看到**所有增量都是 0**，看起来「干净得完美」，其实是**没在统计**。

### 2. `scx_enable` 回读像状态

`/proc/hmbird_sched/scx_enable` 回读的是**用户意图**：

- `hmbird_sched_proc_main.c:285` `WRITE_ONCE(*pval, val)` 先发布意图；
- `:306-307` 写失败（`rc != 0`）**不回滚**意图，直接 `return -EFAULT`；
- 真实状态只出现在 dmesg：`:299` 的 `scx_enable=%d -> hmbird_ctrl() rc=%d, enabled=%d`。

⇒ `cat` 到 1 **不代表**已开启；`cat` 到 0 **不代表**已关闭。`docs/真机验证-opt60.md` 里「回读 0 ⇒ 调度未真正生效」的推论**已被证伪**。

### 3. 累计计数器当队列长度

`hmbird_stats` 里的 `gdsq_cnt` / `pcp_timeout_cnt` / `pcp_ldsq_cnt` / `pcp_enql_cnt` 是**累计计数器**（结构体见 `hmbird.c:307-311`，名称数组 `:290-291`），随 uptime 单调增长。

⇒ 「退出后必须为 0」这种判据**永远为假**；只能用**窗口增量**（退出后 − 启用前），并且要减去同等长度空转窗口的基线。

### 附：两个真实发生过的假 PASS

- t194 轮 `t194-residue.sh` 的窗口增量段因 regex 缺陷（`trailing backslash`）**没跑起来**，那轮 M2 实际上是用 **NODE start/end 快照**替代的（`_audit/成功-t194游戏态启用与退出完整还原.md:89`）⇒ 「跑过了」和「判据过了」是两件事，要分开说。
- `PROC start/end spin=1 fengchi=1` 是 **grep 自匹配**造成的假阳性（实际上没有守护进程在跑），同类假阳性见 `_audit/成功-t194游戏态启用与退出完整还原.md:90`。

## 三、假 FAIL 陷阱（两条）

### 1. `grep` 计数命中历史日志

对**全量** `dmesg` 做 `grep -c`，会把开机以来的历史事件都算进本轮。实例：`t188_ev.sh` 报 `disabled=4 warn=0 pc=1`，实际是把 t190 的收尾关闭和 60.9 s 的历史 `tracepoint_add_func` WARN 算进来了；正确做法是只看本轮脚本自己打的 `RESULT` 行。

⇒ 一律**先记基线行数**（`K0=$(dmesg | wc -l)`），之后只统计 `dmesg | tail -n +$((K0+1))` 的增量。

### 2. `Call trace:` 被当成 WARNING

设备上有一类**周期性** `Call trace:` 打印（每 ~61.4 s 一次：121.84 / 183.28 / 244.72 / 306.16），栈顶是厂商 TEE 通路：

```
 __switch_to -> __schedule -> schedule_timeout -> wait_for_common -> wait_for_completion
 __scm_smc_call [qcom_scm] -> qcom_scm_invoke_smc [qcom_scm] -> prepare_send_scm_msg [smcinvoke_dlkm]
```

⇒ 与调度无关、任何内核上都有。★`warn` 判据只数 `WARNING:`，别把 `Call trace:` 算进去★。

## 四、判据速查表

| 判据 | 怎么读 | 坐标 |
|---|---|---|
| 是否饿死（stall） | `failed to run for` 出现 ⇒ 有任务等待过久；判据本身是 `time_after(jiffies, last_runnable + hmbird_watchdog_timeout)) \|\| watchdog_enable` | `hmbird.c:3486`；常量 `hmbird.c:70`（`120 * HZ`） |
| 是否被内核自禁 | `hmbird disabled finished` **且同一时刻没有配对的** `scx_enable=0 -> ... enabled=0` | `_audit/成功-opt161b上机验证hmbird与scx稳定共存.md:62-72`（D4 判定） |
| hmbird 是否真的开了 | dmesg 的 `enabled=1`，不是 `cat scx_enable` | `hmbird_sched_proc_main.c:299` |
| governor 是否被强切 | `t42:` 增量 > 0 | 判据串 `t42:`；联锁代码 `hmbird.c:5043` |
| 退出是否还原了原值 | `t55:` 出现 ⇒ 内核走了 restore 路径（正确顺序下**不该出现**） | `hmbird.c:3717` |
| 最后一次开关是否成功 | `sw_rec[(sw_idx+4) % 5]`，四元组 = `switch_at / is_success / end_state / switch_reason` | `include/linux/sched/hmbird.h:219`（`MAX_SWITCHS=5`）、`:360-364` |
| 有没有重启/崩溃 | `boot_id` 是否变化；`/proc/last_boot_reason` 是否以 `dump,` / `kernel crash` 开头 | 设备侧 |
| 温度 | `max(thermal_zone*/temp)`，注意单位 0.001 ℃ | 设备侧 |

## 五、禁止项（会直接把 hmbird 关掉或让实验失去意义）

| 禁止 | 原因 | 依据 |
|---|---|---|
| 写 `watchdog_enable` | stall 判据里**直接或上它** ⇒ 置 1 立刻判 stall 自禁 | `hmbird.c:3486` |
| 写 `heartbeat_enable` | 置 1 启动应用保活检测，2500 ms 收不到保活即 `can't detect heartbeat, disable ext` | `hmbird.c:4500` / `:4507` / `:4519-4521`；默认 0 见 `hmbird_sched_proc_main.c:60` |
| 置 `hmbird_gov_veto=1` | governor 写 `scx` 会被否决（`EBUSY`），关闭时恢复原值也会被自家否决拦下 | t188 实测 `refuse_delta=4`（`_audit/成功-opt161b上机验证hmbird与scx稳定共存.md:78-96`） |
| 在 `echo 0 > scx_enable` 返回前写 governor | 关闭路径自身会处理 governor，抢写会污染结果 | `docs/启用与还原-操作手册.md` §二 step3 |
| 强行「固定」`scx` | 历史教训：早期镜像上会整机硬挂 | `docs/changelog.md` 2026-10-09 节第 5 条 |

## 六、行号与注释都会漂移

- 同一个函数在不同 opt 上差几十行；**引用前重新 `grep`**；
- ★连内核自己的注释都在引过期行号★：`hmbird.c:3805` 仍在引 `hmbird.c:4579`（早已漂移到别处），而 `hmbird.c:70` 的常量值本身是 `120 * HZ`；
- `hmbird.c:3669-3671` 的注释仍称 `hmbird_gov_switch_away()` 有「两个调用点（enable 一次 + watchdog workfn 每 60 s 一次）」，**第二处已被 opt160 删除** ⇒ 注释不能当事实，源码才能。

## 七、出问题时抓什么（现场收集清单）

```sh
dmesg | tail -300 > /data/local/tmp/case-dmesg.txt
cat /proc/last_boot_reason
cat /proc/sys/kernel/random/boot_id
cat /proc/hmbird_sched/scx_enable /proc/hmbird_sched/slim_stats /proc/hmbird_sched/hmbird_stats
cat /proc/stat | grep procs_running
for d in /sys/devices/system/cpu/cpufreq/policy*; do echo "$d $(cat $d/scaling_governor)"; done
cat /sys/class/thermal/thermal_zone*/temp
```
