## 一、这一轮到底测了什么（真实游戏 + 全套官方链路）

前一篇（`changelog.md` 2026-10-14「P0 判决」）留下的最高优先级是
「源码定位 hmbird 在线时 cpu5/6/7 连 `taskset` 绑核都跑不动的那一处机制」。
本轮没有继续在合成自旋线程上磨，而是转到**真实游戏态**：把整条厂商链路修好，再看对局的客观数据。

### 1.1 ★先把「官方桥」修好（否则后面全是假数据）★

发现现役内核上，厂商用来把「谁在玩游戏」告诉内核的那条链**是断的**：

| 环节 | 现象 | 根因 |
|---|---|---|
| `game_pid` | 恒为 `-1` | ★内核里**没有任何自动路径**会写它 —— 只能由用户态写★ |
| `cpu_load` | 八核恒 `busy_pct:90 / util_pct:60` | 内核 `have_valid_game_pid=0` 的**早退分支**常量（反汇编 `.text 0x3c8-0x3d0`） |
| `critical_task_name` | 节点**根本不存在** | 需要 `ctn_patch` 先把这个节点"造"出来（mapped critical_task raw） |
| `heavy_task_info` / `rt_info` / `frame_produce` | 全空 | 上面两条的直接后果 |

按厂商自己的 `service.sh` 顺序把 `ctn_patch` + `opgs_daemon` 恢复起来后（`insmod rc=0`），
**四项同时变活**（`dev500` 采样 60 s）：

```
t=10s game_pid=[game_pid=27929 child_num=56]
      critical_task_name=[UnityMain UnityGfxDevice]
      cpu_load=[CPU:0 busy_pct:11 util_pct:2 CPU:1 busy_pct:2 util_pct:0 CPU:2 busy_pct:5 util_pct:5 ...]
      heavy_task=[31956;Thread-30;187 ...]
t=20s cpu_load=[CPU:0 busy_pct:100 util_pct:100 CPU:1 busy_pct:100 util_pct:100 CPU:2 busy_pct:75 ...]
```

★⇒ 结论：`game_pid` 是**整条链的唯一活性开关**，而且**必须用户态写**。
它一活，`cpu_load` 从常量变真值、`critical_task_name` 认得出 `UnityMain` / `UnityGfxDevice`、
`heavy_task_info` 出现 `Thread-30`（第五人格主线程）。★

### 1.2 官方给第五人格的规则（从厂商参数库实读）

```json
"es4g": { "state": true, "isolate": "144,0", "tcount": 4,
          "clist": "4,7,2,3", "partial": true, "fps": 60, "app": 1 }
"pipeline": { "4": "__render__", "7": "Thread-" }
"fixed_critical_task": ["n___render__", "n_Thread-"]
```

## 二、★内核级摘除（`CONFIG_HMBIRD_SCHED_CORE=n`）的真实 ABI 影响：只有 1 个符号消失★

> ★**本节 2026-10-17 当日做过一次更正。** 初版把 3 个符号的 CRC 差异判成"CORE=n 破坏 ABI、
> 禁止使用"，**那个判断是错的** —— 真因是出片时漏跑了本仓出片链路里的「CRC 定点覆写」那一步。
> 更正后的结论见 2.2。原文与被推翻之处保留在 2.1，供后来人对照。★

### 2.1 ★错在哪★

`iso_masks` / `task_is_scx` / `sk_filter_trim_cap` 这三个 CRC 是**本树 genksyms 的自然值**，
CORE=y 与 CORE=n **算出来完全一样**（实测两边都是 `0x9998675b` / `0x61658a4e` / `0x43b2b8f0`）。

而上机版 `opt168` 的 `0xcb6a4c44` / `0xb3071c68` / `0xf5845708` 是**定点覆写后的值**，
来自出片链路里的一道必跑工序（初版漏跑）：

| 符号 | 本树 genksyms 自然值 | 覆写成（厂商 `__versions` 期望值） | 覆写依据 |
|---|---|---|---|
| `sk_filter_trim_cap` | `0x43b2b8f0` | `0xf5845708` | BTF 逐块对比证明 `struct sk_buff`/`sock`/`sock_common` 与出厂一致；`bluetooth.ko` 其余 96 个符号全匹配 |
| `iso_masks` | `0x9998675b` | `0xcb6a4c44` | 布局与出厂逐字段一致：出厂 BTF 的 `struct scx_iso_masks` = 40B / 5 × `cpumask_var_t`（`ex_free@0, exclusive@8, partial@16, big@24, little@32`）；本树 `pahole -C scx_iso_masks` 输出完全相同 |
| `task_is_scx` | `0x61658a4e` | `0xb3071c68` | 实现已与出厂逐指令对齐（`ldr x8,[x0,#832]; cmp &ext_sched_class; cset w0,eq; ret`）；原型 `bool (struct task_struct *)` 纯指针入参 + 标量返回 |

★初版出 opt172 时**只编了内核、直接拿裸 `Image` 去重打包，没走这道覆写**，
于是闸门2 报了两个模块拒载 —— 而我把这个现象读成了"CORE=n 的副作用"。
**构建 rc=0、无任何报错**，正是这条链路最容易静默漏掉的地方。★

### 2.2 ★更正后的实测（走完出片链路四道门禁）★

基准＝`gate168/vmlinux.symvers`（2026-10-15 20:06 构建产物，版本串 `v1.1-opt168`，
与器件 `uname -a` 的 `#75-ack304-v1.1-opt168` Thu Oct 15 20:04:30 **同源**，即上机内核的导出表）。

```
门禁3 gate_crc_diff5 : 等长 + 恰差 12 字节 + 三个连续槽位        OK
门禁2 gate_crc_v2    : 三个槽位读数全 OK                         「可出片」
门禁4 gate_crc_pre   : 新值 x1 / 旧值 x0，三槽位全 OK             「允许继续」

闸门2 gate_vko_crc             : 会拒绝装载的模块 = 0            ✅
全量厂商模块审计 gate_all_modules: 493 个模块全部可装载          PASS（缺失=0 CRC不符=0）

相对现役 opt168（15490 导出）：
  ★CRC 不同 : 0 个★
  ★新增     : 0 个★
  ★消失     : 1 个 → hmbird_transitioning (0x47330ca1)★
    （定义在 kernel/sched/hmbird/hmbird.c:95-96；随 CORE 门控的文件一起不编译）
```

★⇒ **`CONFIG_HMBIRD_SCHED_CORE=n` 的真实 ABI 影响只有一处**：`hmbird_transitioning` 这个导出消失。
全量模块审计显示 **缺失 = 0** ⇒ **没有任何厂商 `.ko` 引用它**，所以不构成拒载风险。★

★对照：初版（漏跑覆写）的读数曾是 `CRC 不同 3 个 + 消失 1 个`，
且 `gate_vko_crc.py` 报 `拒载 = 2`（`bluetooth.ko` / `oplus_bsp_sched_ext.ko`）。
把这组坏读数与上面对照看，就是"漏跑覆写"最典型的指纹。★

### 2.3 机制：CORE 门控了两个头文件的 include

全树只有 **2 个**头文件被 `CONFIG_HMBIRD_SCHED_CORE` 门控（`grep -rl ... --include=*.h`）：

| 文件 | 位置 | 门控内容 |
|---|---|---|
| `include/linux/sched.h` | `:2489-2578` | `#ifdef` → `#include <linux/sched/hmbird.h>` + task 侧 helper 块 |
| `kernel/sched/sched.h` | `:3409-3411` | `#ifdef` → `#include "hmbird.h"`（`struct hmbird_rq` 在 `kernel/sched/hmbird.h:198-219`） |

`include/linux/sched/hmbird.h:167-201` 定义 `struct hmbird_entity`（含 `struct task_struct *task`、
`const struct sched_class *sched_class`、`struct hmbird_sched_task_stats sts`）。

★实测：这两处确实改变了 genksyms 的**可见类型集**，但**没有**改变任何导出的 CRC ——
`struct scx_iso_masks` 在 CORE=y / CORE=n 两种配置下都算出 `0x9998675b`。
厂出的 `0xcb6a4c44` 无法从公开源复现（改成员类型 / 加 `__read_mostly` / `__aligned` / `const` /
数组 / 前置换 TU 上下文均不变）⇒ 这就是它需要"定点覆写"的原因。★

### 2.4 ★顺带查出的三个坑（后来人必看）★

1. ★**漏跑 CRC 定点覆写会伪装成"ABI 被破坏"**★：症状与"CORE 改坏了 CRC"**完全一样**
   （3 个符号 CRC 对不上、两个模块拒载、`构建 rc=0` 且无任何报错）。**判据**：看 `vmlinux.symvers` 里
   `iso_masks` / `task_is_scx` / `sk_filter_trim_cap` 是不是**厂商期望值**；是自然值就是漏跑了。
2. ★**`out-core` 是脏构建目录**★：`out-core/Module.symvers`(10-15 15:35) 与
   `out-core/vmlinux.symvers`(10-16 13:00) 对同一符号给出**不同值** ⇒ 混了 CORE=y / CORE=n 两批 `.o`。
   **`opt169/170/171` 都建在它上面，产物不可信。** 基线一律用 `gateNNN/vmlinux.symvers` 这类**按版快照**。
3. **config 只差一行**：从 `gate168/Image.crc` 抽 IKCONFIG 与 CORE=n 的 `.config` 逐行 diff，
   **只差 2 行**（`CONFIG_HMBIRD_SCHED_CORE=y` vs `# ... is not set`）⇒ 不是别的 config 变化导致的。

## 三、这一轮同时确认成立的架构事实（可复用）

| 事实 | 判据 |
|---|---|
| 厂商游戏调度是**五段链**：内核 sched_class + 5 个厂商 `.ko` + 3 个用户态服务 + 参数库 + 云控注入 | `lsmod` + COSA 实读 + HAL fd |
| **放置权在内核**（hmbird `sched_class` 抢 `select_task_rq`），**决策权在用户态** | P0 判决（§1.4） |
| `game_pid` 是**唯一活性开关**，且**只能用户态写** | §1.1 反汇编 + dev500 实测 |
| `es4g` 真选核**必须 `governor=scx`** | 5 个 `android_vh_scx_*` 钩子；gov=uag 时选核拿不到 |
| 厂商 `.ko` 只依赖 10 个 hmbird 导出符号，且**只有 `oplus_bsp_sched_ext.ko` 一个模块要**；没有任何模块依赖 sched_ext | ELF UND 解析 |
| `game_opt` / `sched_assist` / `sched_walt` **不需要**任何"只有 hmbird 提供"的符号 | 同上 |

## 四、★没有解决的（诚实清单）★

1. **hmbird 在线时 cpu5/6/7 被排除出调度视野** —— 连显式 `sched_setaffinity` 都绕不过；
   本轮没找到那一处机制（候选位置见 `changelog.md` 2026-10-14 §四）。
2. **真实对局 FPS 46.53 不过**，`f234` 1631 MHz 被压 19% —— 压频来源未定案。
3. **`scaling_cur_freq` 口径存疑**：8 线程负载下 policy7 恒 672000，与 `load≈20` 不相称。
4. **对非游戏应用的调度影响**、**长时日常使用对比** —— 都没做。
5. **效果量问题**：本机噪声带 I/O 20%、功率 CV 41%，而该方向的效应量 ≤1~2%
   ⇒ ★多数改动在本机**原理上就测不出收益**★。「测不出收益」是合法结论，不拿体感硬凑。

## 六、★暂缓声明★

> ★本方向（内核态 hmbird 调度类 / 风驰游戏调度）**自 2026-10-17 起暂缓**。★

### 放弃原因：★工程量大、难度高★

具体是三条叠在一起，任何一条单独都还能磨，三条加起来不划算：

1. **工程量**：要让调度真的变好，得**同时**复现五段链（内核 `sched_class` + 5 个厂商 `.ko` +
   3 个用户态服务 + 参数库 + 云控注入）。少一段，数据就是假的 ——
   本轮光是"把官方桥修好"（`ctn_patch` + `opgs_daemon` + `game_pid`）就占掉了大半轮次，
   而修好之后 FPS 仍然不过（§1.3）。
2. **难度**：核心症结（§四 第 1 条：hmbird 在线时 cpu5/6/7 连 `taskset` 都跑不动）
   在 2026-10-14 判死后，本轮**没能定位到机制**；三个用户态开关全部无效，
   也**没有下一个可验证的假设**。
   ★注：内核级摘除（`CONFIG_HMBIRD_SCHED_CORE=n`）这条退路本身是**通的**（§二 更正后：
   相对现役只少 1 个无人引用的导出符号，四道门禁全过、拒载 = 0），
   但它需要重编 + 走完整出片链路 + 重验，工程量与收益不匹配 ⇒ 不作为本轮出口。★
3. **收益不可证**：效应量 ≤1~2%，本机噪声带 I/O 20%、功率 CV 41% ⇒
   ★即使改对了，本机也测不出来★。继续投入等于**用不可证的收益去换明确的工程成本**。

### 状态与后续

- 已上机可用的**最后成果**仍是 `v1.1-opt168`（现役）与 `v1.1-opt162`（第二条路的验证内核）。
- ★本轮由 CORE=n 产出的内核件 `Image.opt172.crc` / `boot-v1.1-opt172-repacked.img`
  本身**过了四道门禁**（拒载 = 0、493 个模块全绿），但它**没有上机**，
  也没有满足《发布规范》的 24 小时观察期 ⇒ 状态按 **📦留档（未上机，仅作记录）**，
  ★不建 tag、不建 Release、不宣告发布★。★
- ★不要拿 `Image.opt172-clean`（未覆写那份）去重打包★ —— 那会得到"构建正常、厂商模块静默拒载"的坏件（§2.5）。
- ★复线条件★（要重启本方向，先满足这三条）：
  1. 有一个**能解释**"为什么显式 `sched_setaffinity` 也不能让任务在 cpu5/6/7 上运行"的机制假设；
  2. 该假设能在**合成负载**上先验证（不必等真实对局，省轮次）；
  3. 出片一律走完四道 CRC 门禁，并以「闸门1 相对**现役版**新增/消失/遮蔽全 0
     + 闸门2 拒载 = 0 + 全量厂商模块审计 493 个 `.ko` 全绿」为放行线。
- ★本仓库其余内容（`scx` 调速器切换那条线）不受影响，仍然有效。★
